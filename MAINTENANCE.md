# 公开副本维护 · Maintaining the public copy

日常工作在本地主本进行。导出区用于发布准备和留存过程记录。公开副本已在桌面独立文件夹建立，仅用于发布和展示框架设计。

1. 仅在用户明确要求升级发布时，按框架和技能的差异同步。自动同步和定时巡检均不启用。
2. 同步入公开副本时一次完成白名单筛选、脱敏和必要内容自检。范围限于框架代码、通用文档、七类通用学术流程和空白模板。排除真实知识与成果、个人信息、凭据、实际项目和业务材料、私有历史，以及白名单外的模块及其介绍、入口、映射和引用。
3. 提交前沿用同步时的核验记录，无需重复人工内容检查或安排独立复查。同步后如有修改，只核新增差异。旧记录仅覆盖原已核验内容，清单和版本记录供下次比对。
4. 平台强制安全检查继续生效。既有拒绝只能通过平台支持的方式解决。提前自检不会解除拒绝。提交可使用本人正常 GitHub 身份。

Day-to-day work takes place in the local primary workspace. The export area is for release preparation and records. The public copy is in a separate desktop folder used for release and design reference.

1. Sync framework and skill changes only when the user requests a release update. Sync and review are unscheduled.
2. At sync time, apply the allowlist, remove sensitive content, and perform the necessary content checks once. The scope is framework code, general documentation, seven academic workflows, and blank templates. Exclude actual knowledge and outputs, personal information, credentials, real projects and business material, private history, and any module outside the allowlist together with its descriptions, entry points, mappings, and references.
3. Use the sync record at commit time without repeating manual content checks or commissioning a separate review. Check only changes made after sync. Manifests and version records support the next comparison and cover the content originally checked.
4. Keep mandatory platform checks active. Use only platform-supported options to resolve earlier rejections. Moving checks earlier leaves prior rejections in place. Commits can use the maintainer’s regular GitHub identity.
